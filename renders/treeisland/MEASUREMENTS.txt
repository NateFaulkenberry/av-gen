Tree of Life - Floating Island: the second art pass, and what each claim is measured against
============================================================================================

Everything here was measured on branch agent/treeart on 2026-09-18 with build/release. The pixels
are not committed (the repository's rule for render evidence); stills.json and preview.json beside
this file regenerate all of them:

    ./build/release/src/avgen --headless --queue renders/treeisland/stills.json
    ./build/release/src/avgen --headless --queue renders/treeisland/preview.json

The five tree GLBs the scene loads are gitignored and must be rebuilt first:

    /Applications/Blender.app/Contents/Resources/5.2/python/bin/python3.13 \
        tools/glowmere_tree_layers.py --in assets/treeisle/tree-of-life-hero.glb --out assets/treeisle

The design rationale is docs/decisions/ADR-339 (materials, placement, cosmos) and ADR-338 (the
original import). Asset provenance is assets/treeisle.manifest.json. The comparison arms are
generated from the deliverable by tools/make_treeisland_arms.py, not hand-edited.


1. WHAT THE .BLEND SAYS, AND THE TWO PLACES THE BRIEF WAS WRONG
--------------------------------------------------------------------------------

The brief sent us to `Tree_Glowmere.blend` on the theory that the authored Glowmere look lived
there rather than in `Tree_of_Life_Hero.blend`.

  ** The two files are byte-identical in content. ** Dumped with Blender 5.2.1 headless -- every
  object, mesh, modifier, material, node, unlinked socket default, colour-ramp stop, node group,
  world and light -- the structural diff of the two dumps is six lines and all six are the
  filename in the header. `Tree_Mythic.blend` and `Tree_Ancient_Natural.blend` are the same size
  to within 1 KB. The presets in validation.json are render-time settings of the Value nodes
  (Magic, Bioluminescence, Natural / Tree of Life, Vein brightness, Root glow), all saved at 1.0,
  and Timeline growth at 300.0 -- which is the Glowmere state. There is no separate source.

The second correction is mine, not the brief's, and it is in §3.

The look, transcribed. Blender is Z-up and the export is Y-up, so every `z` below is the GLB's y:

  leaves    (GLB 3, 4)  emission [0.06, 0.45, 0.70] at strength (Random > 0.94)*1.1 + 0.035
                        base     ramp01( clamp((z-20)/28) + Random*0.23 ), two ramps:
                                 broadleaf  [0.025,0.17,0.12] -> [0.35,0.46,0.22]  olive
                                 peripheral [0.025,0.17,0.12] -> [0.60,0.22,0.13]  terracotta
                        roughness 0.48, subsurface weight 0.08
  tracery   (GLB 2)     emission ramp(z/43): [0.04,0.65,0.40] -> [0.08,0.36,0.42] -> [0.95,0.29,0.10]
                        strength 1.6 * 1.2 = 1.92 on noise(pos, 2.6, detail 3) > 0.53
                        base [0.025, 0.10, 0.08], roughness 0.58
  fungi     (GLB 0, 1)  emission [0.05, 0.65, 0.32] at strength 1.3 where Normal.z < -0.25
                        base mix(copper [0.25,0.105,0.075], teal [0.12,0.38,0.30]) on the same test
                        roughness 0.57
  wood      (GLB 5, 6)  emission strength 0.0 -- it does not glow
                        base ramp.001 [0.018,0.026,0.026] -> [0.18,0.16,0.14] on noise(0.32)
                        roughness 0.58 + 0.32*noise

  `ObjectInfo.Random` is per *instance*, and that is the whole pass. A trap worth recording: the
  wood material has an earlier chain whose ramp is multiplied by a cool [0.38, 0.46, 0.5], which
  reads exactly like the source of the reference's mauve-grey bark. Its output socket is not
  connected to anything. It is dead code.

  The three area lights are NOT decoration. warm canopy key (1.00, 0.85, 0.67) at 43,000 W; cool
  silhouette rim (0.32, 0.72, 0.66) at 44,000 W; trunk reveal (0.83, 0.86, 0.84) at 8,500 W. The
  cream-white in renders/Glowmere.png is the warm key. No material change can produce it.


2. WHAT THE EXPORT PRESERVED BY ACCIDENT
--------------------------------------------------------------------------------

The hero GLB's meshes were tested for contiguous instance blocking -- do all three indices of
every triangle fall inside the same block of V vertices?

  mesh  name                          verts       tris   blocked at V   instances   tris each
  ----  ----------------------------  ----------  -------  ------------  ----------  ---------
  0     HERO | Bark and root fungi        14,400   28,480       180              80        356
  1     HERO | Hanging seed lanterns       2,496    1,248        96              26         48
  2     HERO | Recessed living tracery    35,744   62,826       --                --         --
  3     LIFE | Delicate peripheral lvs   929,394  309,798        18          51,633          6
  4     LIFE | Layered broadleaf canopy 2,209,806  736,602        18         122,767          6
  5     LIFE | Trunk roots and boughs    288,560  577,044        --                --         --
  6     LIFE | Twigs and fine branches   779,056 1,446,188        --                --         --

`instance = vertex // 18` therefore recovers exactly the grouping Blender randomised over. The
builder re-checks this at run time and refuses to write if a future export changes it.

Coverage achieved by the baked masks, against what Blender's produce:

  layer     mask                                     achieved   Blender
  --------  ---------------------------------------  ---------  --------
  foliage   per-leaf Random > 0.94, mesh 3             5.855%     6%
  foliage   per-leaf Random > 0.94, mesh 4             6.070%     6%
  tracery   noise > threshold                         47.0%      47% (calibrated to it)
  lumens    face normal y < -0.25, mushrooms          61.2%      exact (geometric)
  lumens    face normal y < -0.25, seed lanterns      33.3%      exact (geometric)
  twigs     sapwood glow                              12.0%      n/a -- AV Gen-native, see below

  The two noise masks do not reimplement Blender's Perlin; a value noise of the same spatial
  frequency is thresholded to the same coverage, because coverage is the property the picture
  depends on. The twig glow has no Blender counterpart at all -- the .blend gives the twigs the
  same non-emissive wood material as the trunk -- and is the approximation §9 permits for §8's
  "secondary glow". Declared in the tool and in the manifest rather than passed off as extracted.


3. PLACEMENT, AND THE MEASUREMENT THAT WAS WRONG BEFORE IT WAS RIGHT
--------------------------------------------------------------------------------

ADR-338's figures reproduce exactly: root footprint x [-20.21, 17.72], z [-14.87, 18.86] about the
tree's own origin, radius ~20; island 56x; tree at [2.0, 3.2, 1.0].

  ** My first pass at the contact measurement reported 24.4% of root vertices over no island at
  all -- a hard §13 violation. It was an artefact. ** It built the island's top surface by binning
  island *vertices* into cells and taking the max per cell. The grass mesh is 7,467 triangles
  over a 60-unit plateau, so at a 1-unit cell most cells contain no vertex, and every root above
  one of those cells was scored "off the island". Rasterising the island's triangles and
  interpolating the height barycentrically gives 0.0% -- before and after. ** No root was ever
  off the island. ** The brief's §13 concern, and my first confirmation of it, were both wrong.

What is real, measured per 2.5-unit cell over the root footprint, taking the *lowest* root point
in each cell against the island's interpolated top surface there:

  metric                                         ADR-338    ADR-339    §
  ---------------------------------------------  ---------  ---------  ----
  root cells over no island                          0.0%       0.0%   13
  median gap, lowest root to surface                +0.78      -0.28   12
  10th / 90th percentile gap                 +0.17/+2.19  -1.01/+1.24  12
  root cells more than 1 unit clear                 46.0%      15.0%   12
  root cells embedded (gap <= 0)                     8.0%      57.5%   15
  canopy overhang (leaf r99 / island r max)          1.64       1.15   §33.2
  leaf vertices beyond the island's radius          46.3%       8.9%
  twig vertices beyond the island's radius          38.5%       6.5%
  island cover radius (full 72-sample ring)          24.0       35.0
  island max radius / lowest rock                31.0/-38.3  44.3/-54.8
  trunk base y / crown y                        +1.07/78.7  +0.87/78.5

  The 15% that still stand more than a unit clear are the apexes of the root cathedral, which is
  what a root cathedral is. renders/treeisland/contact/ is the frame that settles it: the roots
  visibly enter the soil, and the tracery veins read as cyan glints along them.

Two changes got there, and only two: island scale 56 -> 80 with its recentring translate scaled
with it (z 9.16 -> 13.086), and the tree lowered y 3.2 -> 3.0.

  ** The island was scaled up, not the tree down. ** §14 forbids shrinking the tree and the
  previous brief warned against the island reading as "a tiny floating plate"; enlarging the
  island fixes both at once. The tree's x and z were left alone: sweeping a 3x4 grid of positions
  at scale 80 moved the overhang only between 1.144 and 1.168 and the floating fraction between
  14.2% and 18.3%, so moving the tree buys nothing and costs a diff.

  state is 1x and not 3x.

5. WHAT THE SPLIT COSTS
--------------------------------------------------------------------------------

The tree is five glTF files instead of one, and the baked masks are 45 materials instead of 7.

  layer     meshes  primitives  materials    triangles
  --------  ------  ----------  ---------  -----------
  tracery        1           8          8       62,826
  twigs          1           5          5    1,446,188
  foliage        2          22         24    1,046,400
  lumens         2           4          4       29,728
  wood           1           4          4      577,044
  --------  ------  ----------  ---------  -----------
  total          7          43         45    3,162,186   == the hero export, exactly

  Two of the 45 materials have no geometry: at 6 height bands x {lit, dim} per leaf mesh, the
  top band of each mesh has no *dim* leaves, because `f = clamp((y-20)/28) + random*0.23` puts
  every leaf that high over the last band boundary. Harmless, and left in rather than special-
  cased so that the bucket index keeps meaning the same thing in every layer.

The flatten reports 13 nodes -> 45 entities, 45 meshes, 4 procedurals (43 tree primitives plus the
island's 2), against ADR-338's 4 nodes -> 9 entities. Same 3,162,186 triangles, same 139.6 MB
total, roughly five times the draw calls for the tree.

** No GPU timing is reported for this pass, deliberately. **

ADR-170 is one GPU, one run, minima over repeats. That was not available today. Throughout the
window in which this pass could have been benchmarked the machine carried another agent's
`./build/release/src/avgen` at 45-48% CPU continuously for over an hour, plus its
`avgen_tests [glowmere3]` runs starting and finishing alongside mine.

One benchmark was started anyway -- four arms, 3 repeats, 180 frames, interleaved -- and is
**discarded**, because my own `avgen_tests "~[gpu]"` was pinned at 97-100% of a core for its
entire duration. That is self-inflicted and the number would have been mine to mistrust even
without the other agent. It is not reported, not partially reported, and not adjusted.

A contended number here is worse than no number, so this is the no number. What to run when the
machine is idle, which will produce the table this section should hold:

    tools/gpu-lock.sh python3 tools/render_bench.py \
        examples/treeisland/tree-of-life-floating-island.json \
        examples/treeisland/_compare-original.json \
        examples/treeisland/_ctl-no-cosmos-shader.json \
        examples/treeisland/_ctl-no-stars.json \
        --repeats 3 --frames 180 --size 1920x1080 --tier realtime --wait-idle 600

The three arms beside the deliverable are chosen so the answer is a decomposition and not a
single figure: `_compare-original` is ADR-338's 9-entity scene and isolates what the split costs,
`_ctl-no-cosmos-shader` isolates the background shader pass, `_ctl-no-stars` isolates the point
shells and the far plane they drag with them.

What can be said without a stopwatch, because it is structural rather than temporal:

  * The triangle count is **identical** -- 3,162,186 before and after. The split moved no
    geometry; it only changed how the geometry is grouped into draws.
  * The byte count is identical to within the five JSON chunks: 139.62 MB in one file before,
    139.64 MB across five after.
  * The draw calls went 9 -> 45 entities. ADR-338 measured this scene at 15.96 ms GPU at 1080p
    and noted it was "a draw-call-cheap way to spend a triangle budget"; 45 draws is still a
    small number, but the claim that the split is free is **not** established and should not be
    assumed from that sentence.
  * One new full-screen pass was added (the background shader layer), and four procedural point
    objects became four rather than one. Neither is measured here.


6. WHAT IS NOT MEASURED HERE
--------------------------------------------------------------------------------

  * The island's grass texture is a saturated yellow-green that is outside the Glowmere palette
    §19 asks for. It is the supplied asset's own base colour and §5 forbids redesigning the
    island, so it is left alone and lit rather than repainted. The warm key makes it slightly
    more noticeable than ADR-338's cool key did. Flagged, not fixed.
  * The bright/dim ratio on the leaves is Blender's (1.135 : 0.035, 32:1). At the shipping boost
    the 94% floor still reads as a general cyan wash under the 6% specks. Halving the floor in
    the asset would sharpen the speckle further; it would also be a departure from the .blend,
    so it was not done without the owner looking at both.
  * The five-file split is not free to reason about. If a future edit gives one layer node a
    transform of its own, the tree shears apart in a way that is obvious in a frame but invisible
    in a diff. §7 is the assertion that catches it.


7. THE TEST THAT HAD TO CHANGE, AND WHAT WAS ADDED
--------------------------------------------------------------------------------

No engine code changed in this pass. One existing test did, because the scene it reads changed
shape: tests/unit/test_treeisland_example.cpp.

  * `assetNodes == 2` -> `== 6`. The scene now names the island plus five tree layers. The
    assertion's point is unchanged -- that every asset path is relative and inside the repo, with
    no `~`, no `/Users/`, no `Desktop` -- and it still checks that for all six.
  * `tree->kind == Gltf` -> `== Group`. `tree-of-life` is now the group that carries the layers,
    which is what keeps §16's hierarchy to exactly one transform between island and tree.

Added, because the split creates a failure mode the old test could not see: for each of the five
layers, that it is a Gltf node parented to `tree-of-life`, that its local transform is identity,
and that `nodeWorldTransform(layer) == nodeWorldTransform(tree-of-life)` to 1e-5. That is the
registration property stated as an equation. The existing control still stands -- the island is
asserted to have actually moved between samples (a band, 3 to 30), because every hierarchy check
in the file would pass with the hierarchy deleted if the island stood still.

Full CPU suite on this branch, after `cmake -S . -B build/release` and a rebuild:

    ./build/release/tests/avgen_tests "~[gpu]"

    test cases:    2295 |    2290 passed | 4 skipped | 1 failed as expected
    assertions: 2225088 | 2225087 passed | 1 failed as expected

  Zero failures. Main at the branch point (59b0885c) is 2,295 cases / 2,225,003 assertions, so
  this branch is the same case count -- no TEST_CASE was added -- and 85 assertions more, which
  are the five-layer registration loop plus the four extra asset paths the "relative assets" test
  now walks.

  The run before the test file was updated is worth recording too, because it is the one that
  found the work: 2295 cases | 2287 passed | 3 failed, 2225048 assertions | 9 failed. All three
  cases and all nine assertions were this pass's own -- `assetNodes == 2`, `tree->kind == Gltf`,
  and the seven environment checks in §7 above. Nothing else in the suite noticed the change.
