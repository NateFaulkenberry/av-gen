# ADR-009: Testing framework and strategy

- Status: Accepted (2026-09-08)
- Research: `docs/research/tooling.md` §4, `docs/research/audio-analysis.md` §6,
  `docs/research/offline-rendering.md` §11-12

## Problem

Tests from day one, covering audio loading, analysis determinism, parameters, rendering logic and
the audio -> analysis -> parameter -> scene integration, mostly without a GPU, runnable through
CTest.

## Alternatives considered

1. Catch2 v3 (BSL-1.0; 3.16.0).
2. GoogleTest.
3. doctest.

## Decision

- **Catch2 v3** with `catch_discover_tests` so each test case is a CTest entry.
- Test layout: `tests/unit/` (one file per module), `tests/integration/` (pipeline tests),
  `tests/rendering/` (GPU tests, tagged `[gpu]` and skipped when no adapter is available, so CI
  without a GPU still passes).
- Synthetic signals are generated in `tests/support/` (sine, silence, noise with seeded PCG,
  impulse train, click track); no real-world audio is required for tests. Test WAV files are
  generated by the test binary into a temp directory.
- Every bug fix adds a regression test that fails before the fix.
- Performance: Catch2 `BENCHMARK` for the analyzer hop and parameter evaluation, reported but not
  asserted in 0.1.
- Visual regression (later): headless render of a known scene at a known RenderTime, compared by
  exact hash on the same GPU and a perceptual threshold across GPUs.

## Rationale

- Catch2 has the best CTest integration, built-in benchmarks, and an active organisation behind
  it; GoogleTest is comparable but heavier; doctest's maintenance has been intermittent.

## Consequences

- `ctest --preset debug` runs the whole suite; `ctest -L gpu` runs GPU tests explicitly.
- Compile time of Catch2 v3 is mitigated by the static library and precompiled main.
