This package is the AV Gen engine as a program another program drives: `bin/avgen` plus its shaders, the
published contracts and this documentation. It needs nothing else: no source tree, no editor, no window, no
settings file. A client (an agent, a script, an art pipeline) starts `avgen`, speaks JSON-RPC to it on stdin and
stdout, and gets back JSON: what it built, what it changed, and for renders, images with their hashes.

Read this page first; it is enough to build a project and render it. The reference behind it:

`avgen --describe <tools|errors|schema:project|schema:scene|features|version|all>` prints the same contracts as
JSON from the binary itself, so a client can check that the files it reads match the engine it runs. Some

repository, which you do not need; everything a client must know is stated in these pages.

## Layout

```text
bin/avgen                       the engine (macOS arm64, statically linked; system frameworks only)
bin/shaders/                    the shader library; avgen finds it beside itself
share/avgen/docs/               this page and api/
share/avgen/schemas/            the generated contracts
VERSION.json, THIRD-PARTY.md
```

The folder can live anywhere and `avgen` can be started by any path or through `PATH`. Keep `bin/shaders` beside
`bin/avgen`; to use other shaders set `AVGEN_SHADER_DIR` (searched first). `avgen --version` prints one line.

## Two ways to call it

**`avgen serve --stdio`: a conversation.** One process, one session, many calls; renders run as jobs while the
session keeps answering.

```sh
bin/avgen serve --stdio --root /path/to/work 2> avgen.log
```

**`avgen call`: one shot.** One session, one tool or a list of them, the result printed, the process gone.
Nothing carries over between two `avgen call`s except what was saved to disk.

```sh
bin/avgen call project.create '{"path":"demo","scene":"empty"}' --root /path/to/work
bin/avgen call --calls calls.json --project /path/to/work/demo/demo.json --save
```

`--calls` takes `[{"tool": "...", "arguments": {...}}, ...]` and prints `{"success", "calls": [{"tool",
"envelope"}]}`. Exit codes: 0 success, 1 a tool failed (its envelope is still printed), 2 usage, 7 host failure.
Render jobs started by a call list are run to the end before the process exits.

Both take the session's permissions:

| Option | Meaning |
|---|---|
| `--root <dir>` | A folder the session may read and write (repeatable). Your work folder. |
| `--read-root <dir>` | A folder it may only read (repeatable), e.g. where source models or audio live. |
| `--write-root <dir>` | A folder it may write, and so read (repeatable). |
| `--allow-subprocess` | Tools may start child processes (the `performance.*` profiling family). Off by default. |
| `--project <p.json>` | (`call` only) Open this project first; its folder becomes a read and write root. |
| `--save` | (`call` only) Save the project after the calls if they all succeeded. |

**Paths.** Every file a tool reads must be inside a read root and every file it writes inside a write root, after
`..` and symlinks are resolved; anything else is `PERMISSION_DENIED`. A relative path is relative to the **open
project's folder**, else the first write root, **never the working directory**. stdout carries the protocol
only; the log is on stderr. `serve` opens no socket and listens for nothing.

## The protocol in one paragraph

JSON-RPC 2.0, one JSON message per line. Send `initialize` first (it answers the versions, the API level, your
permissions and `capabilities`), then `tools/call {name, arguments}` as often as you like, then `shutdown`.
`tools/list` returns the catalogue with per-session availability. While a tool or a render job runs the server
sends `notifications/progress`; log lines at or above `initialize`'s `logLevel` arrive as `notifications/log`.
Calls are answered one at a time, in order. Details and every protocol error code:
[api/protocol.md](api/protocol.md).

## Every call answers an envelope

```json
{"success": true, "result": {}, "summary": "created 'column'", "changes": [], "warnings": [],
 "transaction": "tx-3", "job": null}
```

On failure `success` is false, `result` is null, and `error` is `{code, message, recovery, details?}`. A tool
failure is a normal JSON-RPC response, not a protocol error. The codes are a closed set
([api/errors.md](api/errors.md)): branch on `code`, show `message`, follow `recovery`. `details` may carry `path`,
`pointer`, `field`, `findings` or `retryAfterMs`. Read `warnings` too: a call can succeed and still tell you, for
example, that a route overwrites the value you just set.

## Transactions

Every mutating call runs in a transaction. Without one of your own it gets an implicit one: if it fails, the
project is put back and the files it created are removed. For several calls that must land together:

```text
transaction.begin {label}                  -> {id}
tools/call {..., "transaction": "<id>"}    each call names it; a mutating call that does not is refused
transaction.commit {id}   or   transaction.rollback {id}
```

A rollback restores parameters, routes, the timeline, the composition (nodes, lights, environment) and the
sequence; it does not un-import audio or stems, move the playhead or delete render outputs. A tool whose catalogue
entry says `undoable: false` is refused inside a transaction unless the call passes `irreversible: "accept"`. The
full table: [api/transactions.md](api/transactions.md). `dryRun: true` on a `tools/call` checks the name, the
arguments, the permissions and availability and runs nothing.

## Projects and scenes

- A **project** is one JSON file, `<folder>/<name>.json`: the audio, parameter values, modulation routes, the
  timeline, render settings, and a reference to its scene. Schema:
  [avgen-project.schema.json](../schemas/avgen-project.schema.json).
- A **scene** (composition) is `<name>.scene.json` beside it: nodes (glTF models, groups, procedural geometry),
  lights, environment, post. Schema: [avgen-scene.schema.json](../schemas/avgen-scene.schema.json).
- `project.create {path: "demo", scene: "empty"}` makes `<first write root>/demo/demo.json` and an empty scene
  beside it, and opens it. `project.open {path}` opens one; `project.save` writes it. **Nothing is saved for
  you**: not on shutdown, not after a render.
- Edit through tools (`scene.create_node`, `parameter.set`, `camera.set`, `modulation.create`, ...), or edit the
  scene as a document: `document.get {document: "scene"}` returns `{content, hash}`, `document.patch` applies a
  JSON Patch (RFC 6902) and refuses one that would make the scene invalid, and `document.validate` and
  `project.validate` report findings `{severity, code, pointer, message}`.
- **Parameters** are the scene's controls by canonical path: `nodes/<node>/position`,
  `nodes/<node>/emissiveBoost`, `camera/fov`, and the `env`, `post` and other groups. Never guess a path:
  `parameter.search {query}` finds them, `parameter.get {paths}` gives ranges and defaults, and
  `parameter.list_groups` gives the overview. A glTF node has `position`, `rotation`, `scale`, `visible`,
  `emissiveBoost`, `roughnessScale`, `opacity`, `lightIntensity` and `lightColor`; its materials are not
  separate parameters.
- A new project carries the engine's default audio routes (for example `audio.bass -> root/scale`);
  `modulation.list` shows them and `modulation.remove` deletes one by index.

## Asset ids

`asset.import {file}` copies a model (`.glb`/`.gltf`), an HDR environment or a texture into the project's
`assets/<type>/` folder, records it (with its SHA-256 and the optional `source` you give) in
`assets/manifest.json`, and returns its id:

```text
asset://project/models/resonator.glb      ->  <project folder>/assets/models/resonator.glb
```

Every asset-taking argument accepts that id (or a path inside a read root). Ids are relative to the project, so
a project folder can be moved or copied whole. Importing the same bytes again returns the existing id
(`duplicate: true`). A model is loaded before the import succeeds; `result.import` is what the engine found in
it (meshes, materials and their names, rigs, clips, triangles, bounds, `warnings`). The original file is never
modified. Audio goes in with `asset.import_audio {file}` (the project's track) and `audio.import_stem` (below).

## Models: the glTF contract

Y-up, metres, triangle meshes, PBR metallic-roughness, `KHR_materials_emissive_strength`, skins with at most four
influences per vertex, skinned animation only; no morph targets, no node animation, no Draco, no GPU instancing;
name your materials. The whole contract, and what each unsupported feature does to an import:
[api/gltf-export.md](api/gltf-export.md). An export is right when `asset.import`'s `import.warnings` is empty.

## Stems, signals and modulation

The music drives the picture through **signals** and **routes**.

- **Signals** are named values on the engine's bus, updated every frame: the track's analysis (`audio.rms`,
  `audio.bass`, `audio.lowMid`, `audio.mid`, `audio.highMid`, `audio.treble`, `audio.onset`, `audio.beat`,
  `audio.energy`, ...), musical time and events (`music.beat`, `music.downbeat`, `music.build`, `music.drop`,
  `music.impact`, ...), timbre descriptors (`sonic.*`) and one family per stem. `signal.list {query}` lists them
  with their current values and ranges, and whether each is an event (a momentary pulse) or a level.
- **Stems** are parts of the song (drums, bass, ...) used for analysis only, never played.
  `audio.import_stem {file, key, role}` copies one into `assets/audio/stems/` and publishes `stem.<key>.*`:
  `active`, `rms`, `peak`, `level`, `onset` (an event), `onsetStrength`, the five bands `bass`, `lowMid`, `mid`,
  `highMid`, `treble`, then `centroid`, `width`, `onsetLow`, `onsetMid` and `onsetHigh`. `role` (`drums`, `bass`,
  `synth`, `vocal`, `other`) also publishes `role.<role>.*` from the first stem of that role. A stem is compared
  with the mix, and `project.validate` warns when it does not line up.
- **A route binds a signal to a parameter** (modulation):

  ```json
  {"name": "modulation.create", "arguments": {"source": "stem.drums.level", "target": "nodes/column/emissiveBoost",
   "amount": 6, "op": "add", "attackMs": 20, "decayMs": 250}}
  ```

  `amount` is the depth (negative inverts), `op` is `add`, `multiply`, `replace`, `min` or `max`, `attackMs` and
  `decayMs` smooth it, `component` drives one component of a vector, and `envelope` (`peakhold`, `linearfall`)
  turns an event into a decaying value. The result says `bound: true` when both ends resolved; an unbound route
  does nothing, so check it. Only parameters that `parameter.search {modulatableOnly: true}` returns can be
  targets. `project.validate` reports dead routes (`route.dead`).

Signals move while time runs: in a render every frame is evaluated with the audio at that time, so a route shows
in the images, not in a `signal.list` taken between calls.

## Rendering, capture jobs and hashes

`render.capture` (one frame, PNG or EXR) and `render.start` (a range, as a PNG/EXR sequence or a `.mp4`/`.mov`)
render the project **as it is in the session, unsaved edits included**, and return a job id at once:

```text
render.capture {frame: 24, fps: 24, width: 960, height: 540, path: "renders/a.png"}   -> {job: "job-1"}
job.wait {id: "job-1", timeoutMs: 900000}                                            -> the job record
```

- `history: "play"` (the default) renders and discards every frame from 0 first, so frame N has the history of a
  play-through; `"seek"` jumps there (faster; stateful content may differ slightly).
- The record's `result` has `frameHashes` (FNV-1a of each frame's pixels as read back from the GPU, 16 hex
  digits), `frameHash` (the last), `sequenceHash`, `outputs [{path, frame, bytes, sha256}]`, `timing`, `lock`,
  `warnings` and `gpuErrors`. **The frame hash is the identity of a picture**: the same project, frame, size and
  tier give the same hash on the same machine and build, and a capture of frame N equals frame N of a
  `render.start` from 0. Compare hashes, not PNG bytes.
- `job.status`, `job.list` and `job.cancel` never block; `job.wait` blocks only your call (default timeout 30 s;
  pass a longer `timeoutMs` for a first render). At most four jobs are queued or running (a fifth is `BUSY`),
  one on the GPU at a time.
- `render.probe {node, frame?, width?, height?}` answers, without rendering, where a node falls in the frame: use it
  to check a shot before paying for a render.
- **The first render in a process creates the GPU device and compiles the pipelines.** On a cold cache that takes
  minutes (this build's measured figures are in the session below); `notifications/progress` reports the compile
  as `compiling pipelines: <n> of <m> ...`. Later jobs in the same process start in seconds, and compiled
  pipelines are cached on disk for the next process.

A session that never renders never creates a GPU device: everything except `render.capture` and `render.start`
runs on the CPU.

## The GPU lock

GPU work on one machine is serialised by a lock directory that every AV Gen process honours,
`${TMPDIR:-/tmp}/avgen-gpu.lock`. A render job takes it after loading the project and releases it when the job
ends; an idle server holds nothing. You need do nothing for it to work. What you can set:

| Variable | Meaning |
|---|---|
| `AVGEN_AGENT` | Your name, written as the lock's `holder`; other waiters report `waiting for the GPU lock (held by '<name>' (pid <n>))` |
| `AVGEN_GPU_LOCK_TIMEOUT` | Seconds a job waits for the lock before failing `BUSY` (default 3600) |
| `TMPDIR` | Where the lock lives; processes that must share it need the same value |

When a process above `avgen` already holds the lock (a wrapper that took it and then started `avgen`), the job
sees its own ancestor's pid in the lock and runs without waiting (`lock.heldByAncestor: true`). The protocol, for
a client that wants to take the lock itself: [api/protocol.md](api/protocol.md), "The machine's GPU lock".

**A live show holds the lock.** While AV Gen Studio is performing -- an output or projection window open, a
Syphon/NDI share, or performance mode on (reasons `output`, `share`, `performance`; playing the transport or live
audio input alone is not a show) -- it holds this lock (holder `avgen-studio-show`), so your
render job waits in `preparing` with the phase `waiting for the GPU lock (held by 'avgen-studio-show' ...)` until the
show stops (or `AVGEN_GPU_LOCK_TIMEOUT` passes). A session on a host that is itself running a show refuses
`render.*` with `BUSY` and `details {field: "show", reasons: [...]}`, and holds jobs queued before the show;
`session.info.show` says whether a show is running, why, and who holds the lock.

Other variables `avgen` reads: `AVGEN_SHADER_DIR` (a shader folder searched before `bin/shaders`) and
`AVGEN_PIPELINE_CACHE` (the compiled-pipeline cache folder, default `~/Library/Caches/avgen/pipeline-cache`;
`off` disables it).

## Things to know

- **The session's view is the truth.** Read before you write (`parameter.get`, `scene.get_summary`,
  `document.get`) and check every write's result: values are clamped to their hard range and the result says so.
- **One session per `serve` process**, one explicit transaction at a time.
- **Nothing is saved unless you call `project.save`** (or `avgen call --save`).
- **Determinism.** Two processes rendering the same project at the same settings give the same frame hashes on the
  same machine and build; another GPU or build may differ.
