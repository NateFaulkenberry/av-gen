# QA, Regression and Cleanup Pass — 2026-09-22

**Status:** complete for this pass; deferred items listed and not started
**Machine:** Apple M2 Max, macOS 25.6, Dawn WebGPU on Metal, `--preset release`
**Scope:** no new product features. Correctness, regression coverage, dead code, large-file audit.

> Written for the engineers who pick AV Gen up when feature work resumes. It assumes you know the
> codebase but not what the last three weeks did to it.

## Executive summary

Three weeks of very heavy development (**1,948 commits**) left the repository in better shape than
the brief for this pass assumed. There is **no marker debt**: `src/` and `shaders/` contain **zero**
`TODO`, `FIXME`, `HACK` or `XXX` comments across 748 files (the only textual hit is the `XXXXXX` of
an `mkstemp` template in `video_writer.cpp`), every `not implemented` path returns a `Result` error
naming the platform or the limitation, and `[[nodiscard]]` is applied consistently enough that the
19 `-Wunused-result` warnings in the build are all benign discards of counts and handles rather than
dropped failures.

The debt that *has* accumulated is structural and concentrated in one place, and the coverage gap
that matters is not where a test count would suggest.

**The most important finding, and it is a P0:** **saving a project moves its hero anchors, by the
same amount every time, and nothing needed to be edited for it to happen.** One frame of simulation
and one save walks `ember`'s anchor 68.191 m, `sage`'s 5.005 m and `tide`'s 1.550 m; saving the
result does it again, identically, forever. N saves put `ember` 68N metres from where it was
authored. Hero anchors are what the Auto-director frames, so a project that has been saved a few
times is aiming its cameras at empty ground — and the tracked film project
`glowmere-valley-2-multicam.json` is already in that state, with every character's anchor 9–36 m
from its body. It also explains the single genuine test failure in the suite. Found by smoke-testing
`--save-project`, not by any of the static analysis. See *Remaining known bugs*.

**The second most important finding:** `particlesToJson` / `particlesFromJson` — about 445 lines
translating 85-odd fields, including three curve types, a vector of field forces and a scatter-anchor
table — lived in `composition.cpp`'s **anonymous namespace** and had **no direct test of any kind**.
An anonymous namespace is unreachable from a test binary, so the only thing exercising it was
whatever a whole-`Composition` round trip happened to touch, and no test in the repository wrote a
particle system with anything set. A 445-line serialiser for the most-churned file in the codebase
was running unverified. It is now a module with a round-trip fixpoint test.

**The clearest structural finding:** `src/scene/composition.cpp` is both the **largest** file
(11,729 lines) and the **most-churned** (207 commits in three weeks — 20% more than the next file).
Those two facts together, not either alone, are what make it the architectural hotspot: it is the
file every agent working on anything had to edit.

## Phase 2 — correctness

### FIXED — a light rig from a newer format version was silently reinterpreted

`LightRig::toJson` wrote `"version": 1` from the start. `LightRig::fromJson` validated `"format"`
and **never read `"version"`**. A rig written by a later build therefore loaded as though it were
the current revision, with whatever that revision changed reinterpreted rather than reported — the
quiet half of a format break, and the one that produces wrong lighting rather than an error.

Composition files have been checked this way all along (`kFormatName` / `kFormatVersion` in
`composition.cpp`), so the fix is that same check, spelled the same way, in
[light_rig.cpp](../../src/scene/light_rig.cpp). A newer version is refused with a message naming
both numbers; a non-integer version is refused; an **absent** version still reads, because all 20
rigs in `examples/lightrigs/` carry `"version": 1` and only a *newer* version can misread — so
refusing an absent one would break hand-authoring and buy no safety.

Covered by `a rig from a newer format version is refused, not reinterpreted` in
`tests/unit/test_light_rig.cpp`, which also asserts that the version the writer emits is the one the
reader accepts — without that, the check guards a number nothing produces.

### FIXED — a dead knob in the motion variant generator

`VariantOptions::mirror` was a public, documented `bool` that `motion_variants.cpp` **never read**.
A caller could set it and be silently ignored. Alongside it, `strideWarp()` was a complete,
documented implementation that **no caller reached**, and `VariantKind::StrideWarp` was never
produced.

This is the dead-knob family the module's own header warns about, in the module that warns about it.
Both were removed rather than wired: `scene/motion_augment.hpp` had already become the module that
does augmentation (it owns the working `mirrorClip`), `generateVariants` has **no production
callers** at all, and two generators for one job is the worse outcome. The header now says what the
generator actually produces — `Source` and `SpeedWarp` — instead of "§43's list, as far as it is
implemented" beside two things that were not.

### INVESTIGATED, not a bug — five cases worth recording

Each of these looked like a defect and was not. They are here because the *next* person will find
the same signal.

1. **`rainbowToJson` / `sparkleToJson` unused in `atmospherics.cpp`.** Looked like rainbow and
   sparkle effects failing to persist. They persist: serialisation moved to the schema-driven
   `effectPayloadToJson` and the per-effect `floatField` declarations in `comet_effect.cpp` /
   `aurora_effect.cpp`. The hand-written pair are leftovers. **Deleted as dead code.**
2. **`r = SkyRainbow{}` resetting authored state in two effects.** Intentional and documented:
   `applyStyle` is preset application, and a style that sets only what it wants leaves the previous
   style's rainbow on.
3. **`lightRadiance` / `rangeWindow` unused in `path_tracer.cpp`**, both documented as existing "so
   the two renderers agree". Looked like the path tracer ignoring colour temperature and light
   range. It does neither: the logic moved to `pathtrace/lights.cpp` (as `emitterRadiance`, same
   body) and **is** used there. The `path_tracer.cpp` pair are verbatim leftovers. **Deleted.**
4. **`particlesToJson` writes no `name`.** Looked like a lost field, and a consequential one,
   because a particle system's name *is* its parameter path (`particles/<name>/spawnRate`) — a name
   that changed across a reload would silently orphan every modulation route and timeline track
   aimed at the old path. It is deliberate: the owning composition node carries the name, and
   `Composition::rebuild` assigns `node.particles.name = node.name`
   ([composition.cpp:3612](../../src/scene/composition.cpp#L3612)). Putting a second copy in the
   file is what would create the risk. **Now asserted** by `the system's name is the node's, not
   the file's`, specifically so that nobody "fixes" the missing key.
5. **50 apparent bare-statement calls to `readFloat`**, whose `Result` would have been discarded.
   All false positives: `core/wind.cpp` and others define their own **out-parameter** `readFloat`,
   and the rest were multi-line expression continuations. This is `docs/testing.md` entry 15 — a
   `git grep` census that does not understand its own input — and it cost an hour to *not* report.

## Phase 3 — regression protection

### TEST ADDED — particle system persistence (P0)

`tests/unit/test_particle_io.cpp`. The load-bearing assertion is a **JSON fixpoint**: write, read,
write again, require the two documents equal. That catches a whole family at once, *including for
fields added after the test was written*:

* a key written but never read (the reader keeps its default, so the second write differs),
* a key read under one spelling and written under another,
* and an **elision/default mismatch**, which is the one this serialiser is structurally exposed to.

`particlesToJson` omits many fields when they equal a default written as a **literal at the call
site** (`if (s.sizeVariance != 0.3f)`), while the reader's fallback is `ParticleSystem`'s member
initialiser. Those are two copies of the same number in different files. When they drift, a
default-valued system round-trips into a *different* system, with no error anywhere. Nothing but a
round trip can see it, and until now nothing performed one.

The suite has six cases: a fixpoint on the defaults (the elision case), a fixpoint on a system with
every field set to a distinctive non-default, a field-by-field read-back (a fixpoint alone would be
satisfied by a writer and reader that agree on the same *wrong* field), the name contract above, the
absent-object case that every "off is the default" comment in `particles.hpp` promises, and the
malformed-input paths.

Per `docs/testing.md` ADR-182 — a probe that cannot fail proves nothing — the fixpoint is checked
against its own teeth by `the fixpoint notices a field the reader drops`, which plants a missing key
and an extra key in a document and requires the comparator to report exactly one of each.

### TEST ADDED — hero anchors survive a save (P0, `[!shouldfail]`)

`saving a project does not move its hero anchors` in `tests/unit/test_glowmere_multicam_defects.cpp`
pins the P0 in *Remaining known bugs*. It loads the film project, steps **one** frame, and compares
`Engine::projectDocument` — the same function `saveProject` uses, so it cannot be a second
serialiser that happens to agree — against the file on disk, across all 16 heroes.

Two things about it are worth copying:

* **The one frame is load-bearing.** The first version of this test did not step, and it **passed**
  — the anchors are still the file's own until the engine runs. A fixture that never reaches the
  mechanism is `docs/testing.md`'s family C, and this one was written, run, and seen to pass before
  the omission was noticed. The stepped version reports `ember by 68.191 m`, matching the figure
  measured independently through the CLI.
* **It checks every hero, not the five characters.** A save that walks a mushroom's anchor is the
  same defect and would otherwise be invisible.

### TEST ADDED — light rig format version (P1)

Described under *Phase 2*. Covers a newer version being refused, a non-integer version being
refused, an absent version still loading, the format name still identifying the file, and — the
part that stops it guarding a number nothing produces — that the version the writer emits is the
version the reader accepts.

### How this run was validated, because three earlier attempts were not

A suite run is only evidence if the binary did not change under it, and getting that wrong cost
three runs in this pass:

* A 17-minute run was discarded because a queued background build relinked `avgen_tests` four
  minutes into it (`docs/testing.md` entry 1). The guard that catches this is recording the binary's
  mtime before and after and requiring them equal.
* Several queued "wait for idle, then build" tasks each fired a build into the same build directory.
* Killing `ninja` to recover truncated its log, after which **every** build recompiled all ~1,470
  targets and none ever reported "no work to do". This was nearly written up here as a project
  defect — that every incremental build is a full rebuild — before `ninja -d explain -n` showed the
  real cause: `ninja: warning: premature end of file; recovering`. Note that
  `VerifyGlobs.cmake_force` is reported dirty on every build by design and is not a problem.

**Before starting a suite: require a second `cmake --build` to report no work, and check
`ninja -n` shows zero dirty targets.** Both are seconds against a 17-minute run.

## Technical debt discovered

### Coverage distribution, not coverage count

The repository has ~195,000 lines of test code, and a count of it would say the project is
thoroughly tested. The distribution says something narrower.

**The `draw` half of the UI has no tests: 16,346 lines across 20 `src/ui` modules** that no test
references, concentrated in `control_panel.cpp` (4,730), `sequence_panel.cpp` (4,130),
`world_panel.cpp` (1,410), `world_edit_panel.cpp` (1,169) and `viewport_overlay.cpp` (714). Add
`app/application.cpp` (6,240) and `app/ui_script.cpp` (1,290), also unreferenced.

**This is much less alarming than it first looks, and the reason is worth stating**, because a
naive reading of it would send someone off to do work the project has already done. AV Gen has an
established pattern for exactly this problem — **extract the decisions into a `*_logic` module and
test that, leaving only the ImGui calls untested** — and it is applied to fourteen modules:
`ui_logic`, `lights_panel_logic`, `world_edit`, `world_editor`, `world_effects_panel`,
`world_probe`, `edit_history`, `editor_layout`, `gizmo`, `brush`, `unsaved_changes`,
`output_preview`, `particle_weather_rows` and `help_panel`. `test_lights_panel.cpp` is the model:
it tests `lights_panel_logic.hpp` and never touches `lights_panel.hpp`.

So the real finding is narrower and actionable: **the two largest panels have no `*_logic`
counterpart.** `control_panel.cpp` and `sequence_panel.cpp` are 8,860 lines of interleaved decision
and draw, and they are the two panels a user spends all their time in. Extracting their state
decisions the way `lights_panel_logic` already does is the highest-value UI work available, and it
is a pattern-following exercise rather than a design problem.

### Parameter reachability is protected for some families and not others

The standing rule that anything visible in the picture must be findable in the UI has been
**institutionalised** for several families: `test_effect_conformance.cpp` asserts "every parameter a
kind registers is a row the panel can draw" for every atmospheric kind, and
`test_debug_overlay_reachability.cpp`, `test_tree_energy_reach.cpp` and
`test_temporal_conformance.cpp` cover their own. That is real and it works.

There is **no equivalent conformance test for `Composition`'s own `scene/*` family** — the largest
one, covering fog, wind, day/night, water, terrain, ecology lights and cameras. The mechanism to do
it exists and is proven; it has not been pointed at this family. See deferred.

### `spatial::detail` is the shared JSON-reader home and is not named like it

`avgen::spatial::detail` holds the generic JSON readers that `scene/`, `graph/` and `spatial/` all
use. The name says "an implementation detail of the spatial module", which is now false, and a
reader in `scene/` has no reason to look there. **Deliberately left alone**: renaming touches seven
modules and changes no behaviour. Recorded here so the next person does not re-derive it — or,
worse, writes an eighth copy of `readFloat` because they did not find this one.

### Weak assertions found by the compiler

`-Wunused-but-set-variable` flagged two tests that compute a value and never assert on it:
`bestPoseTotal` in `test_cross_clip_matching.cpp` and `redundant` in `test_motion_augment.cpp`.
Both are leftovers where the reported statistic changed (the first reports a median from `bestPoses`
now), so neither test is weaker than it reads. Left alone as cosmetic, but the *technique* is worth
keeping: the compiler will tell you about a test that measures something and forgets to check it.

## Remaining known bugs

### KNOWN BUG — P0 — saving a project moves its hero anchors, cumulatively

**Reproduced, quantified, and now covered by a test.** With no editing whatsoever:

```sh
avgen --project examples/world/glowmere-valley-2-multicam.json --headless --frames 1 \
      --save-project /tmp/resaved.json
```

| hero | save 1 | save 2 | per-save delta |
|---|---:|---:|---:|
| `ember` x | −67.48 → −135.48 | → −203.48 | **68.191 m** |
| `sage` y | 15.17 → 20.18 | → 25.18 | **5.005 m** |
| `tide` y | 6.44 → 7.99 | → 9.54 | **1.550 m** |
| `rook`, `vane` | stable | stable | ~0.003 m (float round-trip) |

The delta is a fixed per-hero offset applied **once per save**, so it compounds without limit.

**It takes one frame of simulation, not merely a save**, and this is the part that makes it hard to
find: serialising straight after a load reproduces *nothing* (checked — the assertion passed). The
first `Engine::update` resolves each hero's anchor from live placement, and the save then writes
that back over the authored value. A round-trip test of the serialiser alone — the obvious place to
look — cannot see it.

**`ember`'s 68.191 m is not arbitrary**: it is exactly the gap between this project's
`nodes/ember/position` override (−56) and the scene's authored node position (12). So the anchor
looks to be re-derived from resolved placement and then have the node override applied again on top
— read A, write A + delta. The y-only drift on `sage` and `tide` is a separate per-hero constant and
is *not* explained by that, so treat the mechanism as a direction for the fix, not a conclusion.

**The codebase already states the principle this breaks**, and has already fixed it once elsewhere.
From [composition.cpp:1717](../../src/scene/composition.cpp#L1717), on reaction bindings:

> An anchor is an authoring fact, and reading it off this instant's finals made it depend on when
> the bindings happened to be taken relative to a project load.

That is this defect exactly, one layer up. The fix direction is established; it has simply not been
applied to the hero-anchor save path.

**Covered by** `saving a project does not move its hero anchors` in
`tests/unit/test_glowmere_multicam_defects.cpp`, tagged `[!shouldfail]` following the house idiom
for a correct invariant the engine does not satisfy (as ADR-260's slope case does). It checks all 16
heroes, not just the five characters, and reports the worst mover by name and metres. It is **not**
fixed here: the repair is an engine change to the save path plus a content repair of the already-
corrupted project, and the second needs an owner decision about what the authored anchors should be.

### KNOWN BUG (consequence of the above) — the multicam control arm reads zero

This is the one genuine test failure in the suite, and it is **not** a test problem. The suite is
correctly reporting a defect in tracked content.

`tests/unit/test_glowmere_multicam_defects.cpp:595`, in `A starred character is not a wall around
itself`, asserts `trapped.size() == 3` and gets **0**. The test's own comment anticipates exactly
this: *"A control that came out zero would mean this arm proves nothing."*

The invariant the test guards still passes — the five characters are navigable and not rejected
`InsideHero`. What fails is the **control arm** that proves the fix is load-bearing, by
reconstructing the removed code path and checking that three specific bodies would have been
trapped by it.

**Why it reads zero.** In `examples/world/glowmere-valley-2-multicam.json`, the project's `heroes`
array (which overrides the scene's) carries anchors at full-precision runtime coordinates —
`rook` at `(-91.00517272949219, 16.79424285888672, -49.31064224243164)` — while the authored node
positions are round numbers like `(-74, 7.62, -18)`. Those are not authored values; they are a
**photograph of a mid-simulation frame written back by an app save**. Every alien's anchor is now
far from its body:

| hero | anchor → body, horizontal | Δy | capsule radius |
|---|---:|---:|---:|
| rook | 35.6 m | +9.17 m | 0.90 |
| tide | 33.8 m | −1.18 m | 0.91 |
| sage | 9.0 m | +7.55 m | 1.02 |
| ember | 14.5 m | +1.15 m | 1.01 |
| vane | 15.9 m | +2.48 m | 0.99 |

Against ~1 m radii, no body is within its own capsule, so `heroPenetration` is 0 for all five and
the control has no defect left to reproduce.

**Why this matters beyond the test.** Hero anchors are what the Auto-director frames: they feed
shot targeting and each hero's `preferredCameraDistance` / `preferredCameraElevation`, and they
supply interest points. Anchors 9–36 m from the characters mean the director is framing **empty
ground**. That is user-visible, and it is in the project used to showcase the character work.

**Not fixed here, deliberately, and it needs an owner decision.** The cause is the P0 above, now
proven rather than suspected. Repairing the content means choosing what the authored anchors should
be, and it is not a mechanical edit:

* Deleting the project's `heroes` array is not an option — the scene's own `heroes` block contains
  `visitor` and ten `*-cap` mushrooms and **none of the five characters**, so the five would stop
  being heroes and the Auto-director would give them no shots at all.
* Setting each anchor to its node position is the obvious repair, but it would then make all
  **five** bodies sit inside their own capsules, so the control's `== 3` — which encodes a
  historical state where `sage` cleared on the vertical test and `ember` was displaced 68 m — has
  to be re-derived at the same time. Changing the `3` on its own would be fixing by hiding.

This is the same defect family already recorded for this exact project: an app save of
`glowmere-valley-2-multicam` photographs the run and writes runtime state back over authored state,
and it has previously done so to `cameraAimFollow` / `cameraShotSpans` (both present and intact in
the file now). **The underlying engine question — that an app save cannot distinguish authored
anchors from simulated positions — is the thing worth fixing, and it is out of scope for this
pass.**

### KNOWN BUG (deliberate, measured) — slope lean depends on heading

`tests/unit/test_character_lab_slopes.cpp` tags `a body's lean on a slope is the same whichever way
it faces` as `[!shouldfail]`. On a 10° slope the lean varies from 2.91° to 7.24° with heading, a
7.17° disagreement against a 1.0° tolerance. The invariant is correct and the engine does not
satisfy it; ADR-260 records that there is no fix inside the current rotation representation. It is
deliberately left failing-as-expected so that it is measured rather than forgotten, and Catch2
shouts if it ever starts passing. **This is the only `[!shouldfail]` case in the suite** and it
accounts for the "1 failed as expected" column — do not mistake it for the genuine failure above.
