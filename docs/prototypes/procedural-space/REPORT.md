# Procedural Space POC: the experiment report

*2026-09-30, for the owner's review. Branch `proto/procedural-space` (not merged). An engineering agent did the architecture, research, engine, audio, profiling, validation and tests; a separate art agent did the look, presets, showcase and Creative Critic runs. Everything below was measured on this Mac (Apple M2 Max, Metal).*

## Summary

**What was built.** The procedural space is an **SDF (signed distance field) ray-marched space**. It runs on AV Gen's *existing* SDF renderer (ADR-027), which was built in September and which no scene had used until now.
- Each space is an ordinary composition scene with one `sdf` node.
- Each is also an ordinary project: its routes, scene states and presets drive the *rules* of that space.
- The engine gained general SDF features: morph, fold, recurse, named nodes, look terms, a march cap, step statistics, compiled trees and fogged edges (ADR-1000 to 1005).
- There is no new renderer, panel, scene type or dependency.

**Headline.** The music changes the rules of the space, not the objects in it.
- Bass sets the nave's width, and mids set the bay's length.
- Each bar re-rules the colonnade.
- Each section changes the kind of space: a hall that folds, a cathedral that contains itself, a kaleidoscope about the line of sight.
- It runs live in the editor at render scale 0.5: the showcase takes 12 ms of GPU time per frame (77 fps).
- It renders offline through the normal pipeline, and two renders of the same range are identical to the bit.

**Look first:** `~/Desktop/av-gen-review/22-procedural-space/showcase.mp4` (3:46, set to Rebuild). Then `showcase-stages.png`, the five `preset-*.mp4` clips, and `ART-NOTES.md`.

## 1. The architecture decision

- **Where it lives.**
  - The spaces are data: `examples/space/*.json` and `.scene.json`, generated by `tools/make_space_presets.py`.
  - The engine changes are general SDF features, in the files that already owned SDFs:
    - `src/spatial/sdf.*` and `shaders/sdf.wgsl`: the tree;
    - `src/scene/sdf_object.*`: the scene object and its parameters;
    - `src/rendering/sdf_renderer.cpp` and `shaders/sdf_raymarch.wgsl`: the render pass.
  - Nothing in the engine is specific to "space".
- **Why there.** AV Gen already had the whole stack, and nothing used it: a data tree, a CPU reference, a GPU interpreter, a render pass with depth composition, and parameters for every node. The smallest architecture that could answer the brief was to become that subsystem's first user, not to build a second one (`ARCHITECTURE.md`, ADR-1000).
- **Which abstraction.** It uses the composition `sdf` node (`scene::SdfObject`), a sibling of the mesh-based `ProceduralGeometry`. Everything else is reused as it stands:
  - named parameters (`sdf/<object>/node/<name>/<field>`);
  - routes from the existing audio bus;
  - scene states and macros;
  - presets;
  - the lit pass, fog, volumetrics, post chain and offline render.
- **Why there is no "Euclidean Space" panel.** The inspector already lists every node as a named parameter (for example `columns/size` and `hroll/amount`), and the World panel already shows SDF objects. A panel would have been the only part of the POC that could not be removed cleanly (§12, §13).
- **Removal.** Delete `examples/space/` and the POC's docs folder. Each engine addition is a self-contained node kind or field, with its own tests and its own rows in `docs/sdf.md`.
- **What promotion to a production feature takes:**
  1. Make `compile: true` the default. The interpreter is about 15x slower on these trees and stays as the reference.
  2. Offer the new node kinds (morph, fold, recurse) in the graph editor.
  3. Fix the existing defect that raymarched SDFs cast no shadow-map shadow. The shadow pass reuses the camera's screen rectangle; a hidden probe documents it.
  4. Make scene states seekable (see §6).
  5. For heavy scenes, two cost items:
     - per-level bounds for `recurse`;
     - temporal accumulation for the volumetric march.
  6. A library of space presets, which is just scene files.

  None of these changes the scene format or the parameter paths.

## 2. Research findings (`RESEARCH.md`)

- **SDF suitability: high.**
  - Booleans, folds, recursion, infinite repetition and smooth blends are each a single expression.
  - Topology changes cost nothing per frame, which is what "the music changes the rules" needs.
  - Meshes (B, C and D in the brief) cannot fold, subtract a doorway or recurse.
- **Ray-marching suitability: high, on two conditions.**
  - The tree must be compiled. The interpreter took 105-254 ms per frame at 960x540; compiled trees take 8-13 ms (ADR-1003).
  - The bound operators must be relaxed. Twist, bend and asymmetric repetition give distance bounds, not exact distances, so the step is scaled by 0.6-0.8 (`march/stepScale`).
- **Alternatives considered.**
  - B, C and D (meshes built on the CPU, on the GPU or in compute) solve a problem the POC does not have, and §31 rules out mesh extraction.
  - E (hybrid SDF and raster) was already the architecture: the pass writes depth, so meshes and particles compose with the space.
  - F (a compiled SDF) was found during the research and then proved necessary (ADR-1003).
- **The techniques that made the space.** These are domain operations applied before the architecture is evaluated:
  - mirrored and finite repetition;
  - a plane fold, `p - 2 min(0, p.n - o) n`;
  - iterated fold, rotate and scale for nested buildings. This stays a true distance bound, because each level divides the distance by its scale;
  - twist and bend about the line of sight;
  - polar repetition about the view axis (the kaleidoscope);
  - a **morph**, a convex mix of two child fields. It is a valid bound and makes "switch structure" a single float.
- **Performance considerations.**
  - Cost is pixels × steps × the cost of one evaluation. Steps are healthy everywhere (19-37 on average), so evaluation cost dominates.
  - Recursion multiplies evaluation cost by the number of levels.
  - The volumetric march for the lamp halos is a fixed cost of about a third of a 1080p frame.

\* **Below 0.5 the numbers stop scaling and are noisy.** Fixed work, such as the volumetric march, sometimes costs *more* at 0.33 than at 0.5. That pattern suggests the GPU clocking down under a light load. Treat 0.5 as the reliable preview figure.

- **CPU frame time** includes waiting for the GPU. The CPU's own work is about 0.5 ms, so every frame is limited by the GPU.
- **Memory:** the process peaks at 0.95-1.03 GB resident. This is unified memory, and includes the decoded song and its analysis.
- **Live editor:** with the showcase playing at canvas scale 0.5 (960x540), the GPU takes 12.3 ms per frame (median) and 15.7 ms at the 95th percentile. The editor shows 77 fps.
- **Offline render at 1080p:** 8.1-15.2 fps. The offline quality tier raises the sky, the volumetrics and the detail limits. The 3:46 showcase takes about 12 minutes to render.
- **Ray-marching safety (§25):**
  - Every object is capped by `march/maxSteps` (160-200), by `maxDistance`, and by an epsilon that scales with distance.
  - At most 0.4 % of rays run out of steps in the architectural spaces, and 1.3 % in Geometry Explosion's emptiest stage. These are rays that graze a surface.

**Profiling findings (Phase 9).**
1. **The kaleidoscope is not a hotspot.** It is the showcase's *cheapest* stage: 19.1 average steps and a maximum of 42.
2. **Recursion is the one real hotspot.** The two cathedrals take the same number of steps as the hall (about 26), but their march costs 2.2-2.8x as much (65-68 ms at 1080p). Every step evaluates the 27-node chamber once per level, six times in all.
3. **The volumetric march is a fixed 16-18 ms at 1080p** (6-7 ms at 0.5), whatever the geometry.
4. **The depth prepass costs nothing,** because the art presets turn it off.

**Why no optimisation was made.**
- Skipping a recursion level when its bounding sphere is farther than the current distance is exact only for exact fields. The chamber uses polar repetition, which is only a bound, so pixels would change.
- The volumetric pass's own levers (resolution, step count) change the halos.
- The art is final, and 8-15 fps offline is acceptable for a POC. Both are promotion items.

## 5. Architectural recommendation

**This should become an implicit-geometry environment: the SDF composition node, promoted, and nothing new.** It is not a shader-layer generator (those have no camera, lights or depth), not a render effect, and not a new scene type.
- **The evidence.**
  - Every visual result above is a scene file plus routes.
  - The engine work was general SDF features. The one real performance problem was solved inside the existing pass, by compiling the tree.
- **What carries over is a "rule layer".**
  - Continuous bands bend continuous rules; bars and phrases flip discrete rules; sections switch the whole rule set.
  - It is already expressible with routes, seeded `random` sources and scene states.
  - A macro (`macros/rules`) scales how much the bands bend the rules, so the music's authority grows over the song.
- **When promoting, build:**
  - the list in §1;
  - a curated preset library;
  - optionally, a "rules" template that the Director or the AI tools can apply to any SDF scene.
- **The hybrid (§32) already works.** Assets placed inside impossible architecture compose through depth today.

## 7. The nesting limit: relaxed (ADR-1005)

- Compiled trees have no stacks, so `SdfTree::validate(SdfEvaluator::Compiled)` skips the interpreter's 8-entry stack checks.
- The depth limit rises from 12 to 16. A compiled tree can now nest up to 15 unary operators, which is enough for the roll, the kaleidoscope, the bend and a second fold together.
- If a compile fails, the renderer falls back to the interpreter only when the tree fits its stacks. Otherwise it skips the object with a warning.
- **No preset changed.** The generator's output is identical, and the 12 validation renders are byte-identical before and after.
- There is one CPU test and one GPU test.

## 9. Open issues and decisions for the owner

1. **Merge the engine additions (ADR-1000 to 1005)?** They are general, tested and removable. Whether to merge the presets is a separate choice.
2. **Seekable scene states.** This is engine work outside the POC.
3. **A fallback tempo clock**, if the spaces should move without music.
4. **The existing SDF shadow-map defect.** `look/shadow` is the workaround for now.
5. **Cost, for live 1080p:**
   - per-level bounds in `recurse`;
   - temporal accumulation for the volumetric march, which would also remove the speckle in the halos.
6. **The GTAO lattice on grazing SDF floors.** The art presets avoid it by turning the depth prepass off.
7. **Rebuild.** The owner's song is in the review media only. Neither the song nor any clip is committed.
